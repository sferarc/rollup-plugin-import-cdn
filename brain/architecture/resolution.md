# Resolution

`resolveId(key, importer)` in `src/index.ts` calls `resolveDependency(key, options)` in `src/load.ts` and returns `dependency.name` when a CDN answered, or `undefined` so Rollup's other resolvers take over. `dependency.name` is the key `resolveDependency` was given: the bare specifier or URL as written, or, in the importer case below, the absolute URL the key resolved to (`src/index.test.ts`, "resolves a relative dynamic import against the CDN module's URL"). `load` receives that id and fetches it again through `loadHook`, which the per-build fetch memo answers without a second request (#14, "fetches a module once for resolveId followed by load").

## One module per served URL

Since the module id is the key as written, a bare specifier that redirects to a URL and a CDN module that imports that URL directly used to be two modules with the same code, so the bundle held two copies and module-level state such as a singleton was split between them. `resolveId` now records, per build, the first id resolved to each final `response.url` together with its body, and returns that id for a later key served from the same URL with an identical body ("bundles a module once when it is imported by bare name and by the URL it redirects to" in `src/rollup.test.ts`). A different body keeps its own id ("keeps two modules served from one URL apart when their bodies differ"), so the code bundled under a key is always byte-identical to what that key's own `integrity` entries were checked against. The map is cleared in `buildStart`. A rebuild from Rollup's cache skips `resolveId` and keeps the ids of the first build, so it does not dedupe anything that build did not.

## Importer handling

The plugin keeps a map from each id it resolved to the `response.url` its source came from, filled in `resolveId` and again in `load` (which a cached rebuild still calls when it skips `resolveId`), and cleared in `buildStart` with the fetch memo. When `key` starts with `./`, `../`, `/` or `//` (`isRelativeReference` in `src/load.ts`), and the importer is in that map or is itself an `http(s)` URL, `resolveId` resolves `key` against that URL and fetches the result as a URL specifier. This covers dynamic imports, which `loadHook` leaves as written ([[import-rewriting]]), so `import("./chunk.js")` inside `react` becomes the chunk's CDN URL rather than a path under cwd. A protocol-relative `//host/x.js` takes the importer's protocol, after redirects (`src/index.test.ts`, "takes the protocol from the redirected importer URL"). Before this, `//` keys hit the `isForeignId` check (`path.posix.isAbsolute` is true for them) and were left unresolved, so the bundle kept a broken import. Any other importer, such as a local file, leaves relative and absolute keys to Rollup without a fetch.

## Which specifiers the plugin claims

`isForeignId` in `src/index.ts` (#14) runs first: `resolveId` and `load` return `undefined` without a fetch for an id that starts with `\0` (another plugin's virtual module) or `node:`, names a Node builtin (`builtinModules`), is a posix or win32 absolute path, or is not an `http(s)` URL and ends in `.html` (`src/index.test.ts`, "skips %s without fetching" for `\0virtual`, `node:fs`, `fs`, `C:\a\b.js`, `index.html` and `pages/about.html`). No CDN serves an HTML page as a module, and the `.html` rule exists for the Vite dev server, described below. The one exception is the importer case above, which `resolveId` checks before `isForeignId`, so a relative or root-relative key whose importer has a known URL is still resolved. `load` has no importer and always applies the check; the `https:` ids that case produces pass it.

For the remaining keys, `resolveDependencyUrls` in `src/load.ts` decides, in this order:

1. A specifier starting with `/`, `.` or `file://` is local: no URLs, so the plugin leaves it to Rollup.
2. A specifier matching `^(http(s)?:)?//` is a URL and is fetched as is. Protocol-relative `//host/...` never gets here, since rule 1 claims it first; it is only fetched after `resolveId` resolves it against a CDN importer.
3. Anything else is a package name. Each entry of `priority` (default `["esm.sh"]` since 0.5.0, `["skypack"]` before, [[decisions/2026-11-01-default-priority-esm-sh]]) yields one URL: `"skypack"` gives `https://cdn.skypack.dev/<key>`, `"esm.sh"` gives `https://esm.sh/<key>` and `"jsdelivr"` gives `https://cdn.jsdelivr.net/npm/<key>/+esm`, both with the version placed the same way, and a function gives `fn(key, version)`, or no URL when it returns `undefined` or `null`, so it can decline a specifier without a request (`src/load.test.ts`, "should skip a custom CDN resolver that returns undefined", "should leave a specifier every custom CDN resolver skips"; `src/rollup.test.ts`, "leaves a module a custom priority function skips to the plugin listed after it"). Any other result that is not a string `URL.canParse` accepts on its own, such as `"lib.js"`, `""` or a number, throws `priority[<index>] returned <value> for <key>; expected an absolute URL or undefined` before any request, which fails the build (`src/load.test.ts`, "should reject a custom CDN resolver that returns %s"; `src/rollup.test.ts`, "fails the build when a custom priority function returns a relative URL"). Before this a relative result went to `fetchImpl`, where the global `fetch` rejected it as a network error and the import was left unresolved behind a warning, and a `fetchImpl` that accepted it gave the module a base `rewriteImports` cannot resolve relative imports against. Before this the result went to `fetchImpl` as is, so a function had to return some URL, and `undefined` was passed to `fetchImpl`, which with the global `fetch` failed as a network error and was warned about. A key that starts with a scheme (`^[a-z][a-z\d+.-]*:`, case-insensitive), such as `virtual:x`, `data:...` or `HTTPS://...`, gets no URL from the built-in entries, since an npm name has no `:`; a function still gets it, so it can map `npm:` or similar itself. With only built-in entries, such a key yields no URLs and is left to the next plugin without a fetch or a warning (`src/load.test.ts`, "should not request %s from skypack", "should not request %s from esm.sh", "should still pass a specifier with a scheme to a custom CDN resolver"; `src/rollup.test.ts`, "leaves a virtual: module to the plugin listed after it"). Before this, `importCdn()` listed ahead of a plugin serving `virtual:greeting` requested `https://cdn.skypack.dev/virtual:greeting` and failed the build on the 404. A key starting with `#`, a package.json `imports` entry such as `#internal`, is treated the same way: the built-in entries give it no URL, since no npm name starts with `#` and in a URL everything after it is a fragment, so the request went to `https://cdn.skypack.dev/` with `#internal` dropped (`src/load.test.ts`, the same "should not request %s" cases; `src/rollup.test.ts`, "leaves a #subpath import to the plugin listed after it").

Outside the importer case above, a path without a leading `./` is treated as a package name, with one exception: an entry (no importer) that is not an `http(s)` URL and names a file relative to cwd, as is or with `.mjs` or `.js` added (the extensions Rollup's default resolver tries), is left to Rollup without a fetch (`isLocalEntry` in `src/index.ts`, `src/rollup.test.ts` "leaves a cwd-relative entry path to Rollup instead of fetching it"). Before this, the README's own `input: "src/index.js"` was requested from `https://cdn.skypack.dev/src/index.js` and the build failed with HTTP 404. A stat that throws, which `throwIfNoEntry: false` allows for anything but ENOENT (ENAMETOOLONG for a path segment over 255 bytes, EACCES), counts as not a file, so the id goes on through the rules above. Before that, a `virtual:` entry with a 300 character name failed the build with `ENAMETOOLONG` from `resolveId` instead of reaching the plugin serving it (`src/rollup.test.ts`, "leaves a virtual: entry too long to be a file name to the plugin listed after it").

## Version pinning

`splitSpecifier` in `src/load.ts` splits a bare specifier into the package name (`pkg` or `@scope/pkg`) and the rest. The name stops at `?` or `#`, so `preact?dev` (an esm.sh query option) is package `preact` with the rest `?dev`: the package pin applies and the version goes before the query, `https://esm.sh/preact@10.19.3?dev`, and the jsdelivr builder moves the query after `/+esm` (`splitQuery`). Before this the query was read as part of the name, so the pin on `preact` was dropped, and an exact `"preact?dev"` entry put the version inside the query (`https://esm.sh/preact?dev@10.19.3`) (`src/load.test.ts`, "should place the version for %s after the package name", "should pass the package's pinned version for a specifier with a query to a custom CDN resolver"). `pinnedVersion` looks up `versions` by the exact specifier first, then by the package name, so a pin on `react-dom` applies to `react-dom/client`. A specifier that carries its own version (`react-dom@18/client`) only takes an exact-specifier pin. Only own entries count: `pinnedVersion` reads `versions` through a `Map`, so a package named `constructor` or `toString` does not pick up the `Object.prototype` member as its version (`src/load.test.ts`, "should not pass an inherited name in versions to a custom CDN resolver"). The skypack, esm.sh and jsdelivr builders put the version after the package name, `https://cdn.skypack.dev/react-dom@18.2.0/client`, `https://esm.sh/react-dom@18.2.0/client` and `https://cdn.jsdelivr.net/npm/react-dom@18.2.0/client/+esm`, and leave a specifier with its own version unchanged (`src/load.test.ts`, "should build the esm.sh URL for %s", "should build the jsdelivr URL for %s"). Custom CDN functions get the same version as their second argument and build the URL themselves (`src/load.test.ts`, "should place the version for %s after the package name", "should pass the pinned version to a custom CDN resolver").

These URLs end the version with `/` or the string end, so `isPinnedUrl` matches them and the `cache` option applies ("should cache a subpath pinned through its package name").

## Fallback

`resolveDependency` tries the URLs in order. When `cache` is set and the URL matches `isPinnedUrl`, `readCache` runs before the fetch and a valid entry returns its `url` and `main` without one; after a successful fetch, `writeCache` stores them (#7, `src/load.test.ts`, "should not refetch a pinned URL on the next resolve", "should not cache error responses").

A missing cache file is silent. Any other read failure (invalid JSON, `EACCES`, `EISDIR`) or an entry without an http(s) `url` and a string `main` emits one warning naming the cache file, the CDN URL and the reason, then falls through to the fetch. A failed write warns the same way and removes its temporary file. No cache failure throws (#29, "should resolve without output when the cache entry is missing", "should warn once and refetch when the cache entry is not JSON", "should warn and leave no temporary file when the cache directory cannot be created"). Before #29 read failures were silent and write failures went to `console.debug`.

Warnings and debug messages go through a `Logger` (`warn`, `debug`) that `resolveDependency` and `loadHook` take as an optional last argument and drop when omitted. The plugin passes one wired to the hook context: `this.warn`, which Rollup tags with `code: "PLUGIN_WARNING"` and `plugin: "plugin-import-cdn"` and routes to `onwarn`/`onLog`, and `this.debug`, skipped on Rollup 3 before 3.25 where it does not exist (`src/index.ts` `contextLogger`). Every failed attempt, HTTP or network, is logged at debug level before the next CDN is tried. No `console` call remains in `src/` outside tests ("reports CDN network errors through Rollup's log handlers" in `src/rollup.test.ts`, "should drop debug messages on a Rollup without this.debug" in `src/index.test.ts`). Before this, both warnings used `console.warn` and bypassed Rollup's log handlers.

Otherwise it calls `fetchImpl`. The first OK response whose `text()` does not throw wins, and its `response.url` is recorded so redirects are followed for later rewriting ([[import-rewriting]]). Every other attempt is recorded with its URL and reason, and the next URL is tried: `HTTP <status>` for a non-OK response (#6, 803e533), `Skypack could not build the package (<url>)` for an OK response whose final URL is a Skypack build error (see Skypack below), or the thrown error's message with its `cause` message in parentheses, since undici's `fetch failed` keeps the DNS, TLS or proxy reason there ("should try multiple CDNs in priority order", "should fall back to the next CDN when one responds with an error").

When `integrity` has an entry for the requested URL or the final URL, `verifyIntegrity` in `src/integrity.ts` checks the body after a successful fetch and after a valid cache read. A cache entry whose recorded `url` is a Skypack build error is skipped too, so one written before that check is refetched. A cache hit for a requested URL that has an entry is skipped, and the URL refetched, unless the cached `url` equals the requested URL or has its own entry: the cached `url` becomes the base for relative imports, so an edited one could point them at another origin with `main` still matching ("should refetch when a cache entry for a checked URL points its imports elsewhere"). A mismatch throws straight out of `resolveDependency`: the check sits outside the fetch `try`, so it is not recorded as an attempt and the next URL is not tried, and a fetched body that fails is not written to the cache (`src/load.test.ts`, "resolveDependency integrity").

When no URL succeeds and any CDN answered non-OK, it throws an error with one `[rollup-plugin-import-cdn] Failed to fetch <name> from <url>: <reason>` line per attempt, network failures included, and `cause` set to the last thrown error; the build fails ("should throw naming the URL and status when the CDN responds with an error", "should throw listing every attempt when HTTP and network failures mix"). Only when every attempt threw does it warn `Could not resolve dependency <name>`, through the logger above, followed by the same lines and return `null` ("should return null when all CDNs fail", "should warn with every URL and the underlying cause when all CDNs are unreachable"). Before #25, thrown errors went to `console.debug`, the warning named no URL, and the thrown error named only the last non-OK URL.

Adding a built-in CDN means extending `AvailableCDNs` in `src/types.ts` and the `parseCDN` map in `src/load.ts`. Today there are `skypack`, `esm.sh` and `jsdelivr`.

## Vite

Vite runs its core plugins, `vite:resolve` included, before a plugin without `enforce`, and `vite:resolve` returns `{ external: true }` for any `https://` id. So under `vite build` a direct URL import, and every absolute URL `loadHook` writes into a CDN module, stayed a runtime import: the bundle kept `import ... from "https://..."` and nothing behind it was tree-shaken (Vite 8.3.4, `src/vite.test.ts`, "bundles URL imports instead of leaving them to Vite as externals", which fails without the fix). A plain `enforce: "pre"` was not enough: the plugin then saw `vite/modulepreload-polyfill` before Vite and failed the build on Skypack's 404.

The plugin object now carries `enforce: "pre"` and a `configResolved` hook that sets `isVite`; Rollup ignores both. Under Vite, `resolveId` first offers a key that is not an `http(s)` URL to the other resolvers through `this.resolve(key, importer, { skipSelf: true })` and returns their answer when there is one, so an installed package and Vite's own modules resolve as before and only bare names Vite cannot resolve are fetched ("leaves installed packages and Vite's own modules to Vite"). `load` under Vite only handles ids in `moduleUrls`, the ids `resolveId` returned, because running first it would otherwise fetch another plugin's unprefixed virtual id such as `~virtual/greeting` ("leaves an unprefixed virtual id to the plugin that resolved it"; that test fails on the old code too, with the plugin listed first). Plain Rollup keeps the plugin-order behaviour described above.

Under `vite dev` (Vite 8.3.4, `src/vite.test.ts`, "Vite dev server"), import analysis rewrites a bare name the plugin resolved to `/@id/<name>`, and the browser's request for it reaches `load` as the id `<name>`, so bare imports inside a CDN module also go through the plugin. URL ids are left as written: Vite does not resolve an `https://` specifier in user code, and an absolute URL `loadHook` wrote, or a relative dynamic import `resolveId` turned into one, stays a URL the browser loads from the CDN, outside the plugin and outside `integrity`. Vite runs `buildStart` once per server, so `configResolved` also sets `isViteServe` from `config.command`, and under it the fetch memo drops a rejected request, so a network error on one page load is retried on the next instead of failing every reload until a restart ("refetches a failed request on the next page load", which fails without the drop). A response with status 408, 429 or 5xx is dropped the same way (`isTransientStatus` in `src/index.ts`; "refetches a 503 response on the next page load" and its 429 case fail without it), and so is an OK response whose body is an HTML page (see HTML pages below), while a 404 or another non-OK status stays kept for the server's lifetime ("keeps a 404 for the server's lifetime"), so a package missing from a CDN costs one request per server rather than one per reload. With no `build.rollupOptions.input`, Vite 8.3.5 resolves `index.html` as an entry in `buildStart` (`DevEnvironment._registerInputsAsSafeModules`, with `isEntry` and `scan` set and the importer `<root>/index.html`) and ignores a failure. When the root has an `index.html`, Vite's resolver answers first; when it has none, as in a middleware-mode server a framework owns, the plugin fetched `https://cdn.skypack.dev/index.html` and every other priority entry on each server start, one timeout per CDN when the network hangs. `isForeignId` now skips any non-URL id ending in `.html`, so no request is made ("does not fetch index.html when the root has none", which fails without the rule).

## HTML pages

A captive portal, a proxy's block page or a CDN's soft error page can answer HTTP 200 with HTML. Before this, `resolveDependency` returned that body as the module, and with `cache` set wrote it under the pinned URL, so every later build read the page back from disk and failed at parse time in `loadHook` until the cache file was deleted. `isHtmlPage` in `src/load.ts` now matches a body that starts, after whitespace or a byte order mark, with `<!doctype html`, `<html`, `<head>` or `<body` followed by whitespace or `>`, case-insensitive. Such a response is a failed attempt like a Skypack build error: the next CDN is tried, a build with none left fails with `served an HTML page instead of a JavaScript module (<final url>)`, and the page is neither cached nor used from a cache entry written before the check (`src/load.test.ts`, "HTML pages"). No module can start with `<`, since HTML-like comments are not allowed in module code, so a real module is never rejected; the narrower tag list keeps an SVG or XML body that another plugin transforms (`src/load.test.ts`, "should keep %j"). Under `vite dev` the fetch memo also drops a response whose body is an HTML page, so signing in to a portal and reloading fetches again (`src/vite.test.ts`, "refetches an HTML page on the next page load"). Markup the check does not match, such as `<div>`, still reaches `rewriteImports` and fails with the parse error hint in [[import-rewriting]].

## jsDelivr

The `jsdelivr` URL shape was checked against the live CDN with `curl` on 2026-10-26: `/npm/<name>[@<version>][/<subpath>]/+esm` answers 200 for plain, scoped, major-only and subpath specifiers (`react-dom@18.2.0/client`, `preact@10.19.3/hooks`, `nanoid@5.0.7/non-secure`), resolving the subpath through the package `exports` (the `Original file:` banner of `preact/hooks` names `hooks/dist/hooks.module.js`), and 404 for an unknown package. Imports inside the served code are root-relative and pinned, such as `/npm/react@19.3.1/+esm`, so `loadHook` rewrites them against the module URL ([[import-rewriting]]) and `isPinnedUrl` matches them for the `cache` option. An unpinned `/npm/react/+esm` is served without a redirect, so its `response.url` differs from the pinned URL that `react-dom` imports and the per-URL dedupe above cannot merge them: without `versions`, a bundle holds two copies. With `versions` pinning both to the same version they are one module (`src/rollup.test.ts`, "bundles a jsdelivr package once when versions pins it to the path its dependents import"). The `+esm` banner also advises against SRI, since jsDelivr generates the file and may rebuild it; the README says so under Integrity.

Checked with `curl` on 2026-11-01: a package jsDelivr cannot bundle, such as `fsevents@2.3.3`, answers HTTP 200 at its `/+esm` URL with a module that opens with a `/** Failed to bundle using Rollup ... */` comment and throws the same message, served `immutable` for a year. Before the check in `resolveDependency` (`jsdelivrBuildError` in `src/load.ts`), the plugin bundled that module, so the build passed and the bundle threw at runtime, and with `cache` set the module was cached under the pinned URL. It now counts like a Skypack build error: the next CDN is tried, a build with none left fails with `jsDelivr could not build the package (<reason>)`, and such a response is neither cached nor used from a cache entry written before the check (`src/load.test.ts`, "jsDelivr build errors"). Only a `cdn.jsdelivr.net` URL whose path ends in `/+esm` and whose body starts with that comment matches, so a module that mentions the message later, a plain file such as `/npm/x@1.0.0/index.js` and the usual `Bundled by jsDelivr` banner are kept. Under `vite dev` the response stays in the fetch memo like a 404, since jsDelivr serves it unchanged until the package changes.

## esm.sh

Checked with `curl` on 2026-11-01. `https://esm.sh/<name>[@<version>][/<subpath>]` answers 200 with a stub that re-exports one pinned build path, such as `export * from "/react@18.2.0/es2022/react.mjs"`, with no redirect: the build path is in the `X-ESM-Path` header and the body. An unpinned name gets the latest version's stub (`https://esm.sh/react` re-exports `/react@19.3.1/es2022/react.mjs`). An unknown package, an unknown version and a missing subpath answer 404 in plain text (`package '...' not found`, `version 99.0.0 of 'react' not found`, `could not resolve build entry`), so the usual non-OK fallback applies and no esm.sh-specific failure check is needed; a package that cannot run in a browser, such as `fsevents@2.3.3` or `sharp@0.33.0`, still answers 200 with a stub. The build files are minified with no space before the specifier (`import*as __0$ from"/react@18.2.0/es2022/react.mjs"`), which es-module-lexer reads like any import.

Dependents import a dependency by the same pinned build path its own stub re-exports, so unlike jsDelivr (above) a package imported by name and by a dependent is one module without `versions` (`src/rollup.test.ts`, "bundles an esm.sh package once without versions, since its stub and dependents import one build path"). Two kinds of import inside esm.sh code are not pinned, so `cache` never stores them and an offline rebuild still requests them (`src/rollup.test.ts`, "refetches esm.sh range and /node/ imports on an offline rebuild with the on-disk cache"): a dependency by range with a target query, such as `/scheduler@^0.23.0?target=es2022` in `react-dom@18.2.0`, a stub for the newest matching release, and Node polyfills such as `/node/process.mjs`, which `fsevents` and `node-sass` import. The rewrite in `loadHook` resolves the range with `URL`, so its spelling depends on the Node version: Node 22 keeps `/scheduler@^0.23.0?target=es2022` and Node 24 encodes it as `/scheduler@%5E0.23.0?target=es2022`; esm.sh serves the same stub for both forms, and the test builds the expected URL with `URL` so it passes on either. esm.sh's `?deps=` query pins such a dependency: `https://esm.sh/react-dom@18.2.0?deps=scheduler@0.23.2` imports `/scheduler@0.23.2/es2022/scheduler.mjs` and a build path under `/react-dom@18.2.0/X-<deps>/`, both pinned, and the plugin places a `versions` pin before that query (`src/load.test.ts`, "should build the esm.sh URL for %s"). The polyfills have no pinned form that is known.

## Skypack

Checked with `curl` on 2026-10-26. A package Skypack cannot build answers HTTP 200 after redirects ending at `https://cdn.skypack.dev/error/build:<name>@v<version>-<hash>`, with a module that `console.warn`s and throws `[Package Error] ... could not be built` on import (`vue@3.4.0`, `zod@3.23.8`). Before the check in `resolveDependency` (`isSkypackError` in `src/load.ts`), the plugin bundled that module, so the build passed and the bundle threw at runtime, and with `cache` set the error module was cached under the pinned URL. It now counts like a non-OK response: the next CDN is tried, and with none left the build fails (`src/load.test.ts`, "Skypack build errors"). Only the `cdn.skypack.dev` host and a first path segment of `error` followed by a `<kind>:` segment match; the `:` keeps a package named `error` out, since npm names have none.

The same day Skypack served `react@17.0.1` for `react@18.2.0`, `react@18.3.1`, `react@19.0.0` and `react-dom@18.2.0/client`, with the version only in its comment banner and its `/-/react@v17.0.1-.../` import, and answered HTTP 404 for `preact@10.24.0` while `preact@10.19.3` worked. Since then a Skypack URL whose path pins an exact version (`<name>@x.y.z`, optionally `-prerelease`) counts as a failed attempt when the served code has a `/-/<name>@v<other>-<hash>/` import but none for the pinned version (`skypackServedVersion` in `src/load.ts`): the next CDN is tried, a build with none left fails with `Skypack served version <other> instead`, and such a response is neither cached nor used from a cache entry written before the check (`src/load.test.ts`, "Skypack served versions"). Rechecked with `curl` on 2026-10-28: `react@18.2.0`, `react@17.0.2` and `react-dom@18.2.0/client` still served 17.0.1, `preact@10.19.3` served itself. Ranges such as `react@18`, unversioned names and bodies without a `/-/<name>@v` import are not checked, so `import "react"` without `versions` still gets 17.0.1 when `priority` lists `"skypack"` first. This is why the default `priority` is `["esm.sh"]` from 0.5.0 ([[decisions/2026-11-01-default-priority-esm-sh]]); unknown whether this is lasting.

Checked with `curl` on 2026-11-01: the banner of a Skypack stub lists a "Pinned URL" such as `/pin/react-dom@v17.0.1-<hash>/mode=imports/optimized/react-dom.js`, served with `max-age=31536000`, which is another stub importing the `/-/react-dom@v17.0.1-<hash>/...` module. `isPinnedUrl` matches both path forms, so with `cache` set a `/pin/` import builds offline once cached (`src/load.test.ts`, "should cache the pinned URL pin/...").
